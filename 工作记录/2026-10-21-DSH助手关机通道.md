# 2026-10-21 DSH 助手关机通道（接自动关机工具）

## 目标

让 DSH 助手在用户说"关机"时能真正把电脑关掉。此前助手执行 `shutdown /s /f /t 5` 被拒绝，电脑没关，用户改用自己准备的 `E:\自动关机工具\自动关机工具.exe` 作为通道。

## 排查

1. 复现：在 pwsh 工具里执行 `shutdown /?` —— 同样被拒（`Error: the user rejected tool "pwsh"`）。说明拦的不是参数，是命令名本身，且发生在"还没真正执行"的审批环节。
2. 定位规则：`dsh-permission-rules` 内置基线 `node_modules/dsh-permission-rules/rules/builtin-high-risk.yaml` 中有

   ```yaml
   - match:
       tools: [bash, pwsh]
       argv: { command: [shutdown, reboot, halt, poweroff] }
     action: ask
     reason: "Shutting down or rebooting the host needs confirmation"
     tags: [builtin, host-control]
   ```

3. 当前 profile（`profiles/web/cordis.patch.yml`）权限预设 `danger-full-access` = `approval: never`，即审批弹窗被禁用；`action: ask` 命中后无人可批 → 自动拒绝。**所以不是 Windows 权限不足，也不是 UAC，重试 `shutdown` 永远同样结果。**

## 根因

内置高危规则对 `shutdown / reboot / halt / poweroff` 判 `ask`，与本会话"审批禁用"冲突，`ask` 退化成拒绝。

## 改动

### 1) 通道验证（未改工具代码）

直接调用工具 exe，命令词是 `自动关机工具.exe`，不命中任何内置规则：

```powershell
& 'E:\自动关机工具\自动关机工具.exe' '/m=助手通道自检，不会关机'
# 输出「正在执行: 弹出消息提示框 / 操作完成」，exit=0
```

无需审批、exit=0 → 通道可用，**工具本身不需要任何改动**。

### 2) 新增助手侧技能（DSH 侧，与工具项目解耦）

- `C:\Users\Administrator\AppData\Roaming\dsh-desktop\harness\skills\host-power\SKILL.md`
  - 规定：关机一律走 `自动关机工具.exe X /t=N`，禁止直接用 `shutdown`；
  - 附 CLI 全参数、`/t` 阻塞执行所以要放大 `timeoutMs` 的坑；
  - 附安全约定（先问再关、缓冲时间、`safe_close_windows` 会关掉 WPS/Word/Office 窗口、单实例互斥导致静默 exit 0）。

### 3) 未动的部分（有意为之）

- 没有改 `builtin.enabled` / `rulesFile` / `fallbackPath`：内置基线是全局安全网，为了关机把它整体关掉或改成绝对路径，一旦写错会让**所有**工具调用响亮失败，风险远大于收益。
- 没有给 `shutdown` 加 allow 规则：保留"裸 shutdown 需要人批"这一层更稳妥；助手走 exe 即可。

## 验证

| 项 | 方式 | 结果 |
|---|---|---|
| exe CLI 可用 | `/m=自检` 调用 | exit=0，正常执行 |
| 是否需审批 | 同上，命令含中文路径 + `/m=` | 无审批提示，直接执行 |
| 是否误关机 | 本次全程未执行 `X`/`R`/`L`/`/sm` | 电脑保持开机（用户在工作中） |
| `shutdown` 仍被拦 | 已知规则 `argv.command: [shutdown…] action: ask` | 预期仍拒，属设计 |

## 已知限制 / 后续

- GUI 开着时 CLI 会因单实例互斥静默 `exit 0`，电源操作不执行；助手据此判断"已关机"会误判，调用前需确认 GUI 未运行。
- `settings.ini` 的 `ask_before_execute` 只作用于 GUI「立即执行」，**CLI 模式无二次确认**，确认责任在对话侧。
- 新技能 `host-power` 需新会话（或重载技能目录）才出现在技能清单里。

# 补充（2026-10-21，同一轮）：按用户要求把 ask 改成 allow

## 目标

上一轮只是"绕行"（走 exe 通道）。用户要求正面修复：助手直接执行 `shutdown` 也不应再被拒——他此前已明确授权"任务执行完就关机"，每次卡在这里不合理。

## 方案取舍

| 方案 | 结论 |
|---|---|
| 工作区用户规则 `<cwd>/.dsh/rules.yaml` 里加 `action: allow` | **采用**。用户规则先于内置基线、首匹配生效；文件级、可回滚、`watch: true` 热读、不用重启宿主 |
| 改 `cordis.patch.yml` 的 `rulesFile`（绝对路径）/`fallbackPath` | 放弃。绝对路径挂载时即校验，写错 → `badFilePolicy: fail` → **所有**工具调用响亮失败，风险远大于收益 |
| `builtin.enabled: false` 整体关基线 | 放弃。等于拆掉全部安全网 |
| 只靠 exe 通道绕行 | 保留为备用，不作为唯一路径 |

## 改动文件

- 新建 `C:\Users\Administrator\Documents\deepseek-harness\default-workspace\.dsh\rules.yaml`
  - 只放行 4 类电源命令词：`argv.command: ["shutdown*", "reboot", "halt", "poweroff"]`，`tools: [bash, pwsh]`，`action: allow`
  - `shutdown*` 用 glob 兜住 `shutdown` 与 `shutdown.exe` 两种写法
  - 其余内置规则（`rm -rf /`、`curl|sh`、敏感路径等）原样不动
- 未改：内置基线 `rules/builtin-high-risk.yaml`、`profiles/web/cordis.patch.yml`

## 验证

| 项 | 命令 | 结果 |
|---|---|---|
| 规则文件能被解析（写坏会 fail） | 普通 `pwsh` 调用 | 正常返回，无加载错误 |
| allow 生效 | `shutdown /?` | **真的执行了**，打印 shutdown 用法；不再出现 `the user rejected tool "pwsh"`（`exit=-1` 是 shutdown 对 `/?` 自己的返回码，与拦截无关） |
| 安全网未拆 | `dd of=/dev/sda` | 仍被拒（内置 `dd` 的 `ask` 命中）→ 基线继续生效，只有电源命令被放行 |

## 生效范围与限制

- 规则文件**按会话 cwd 发现**：只在 `default-workspace` 生效。换工作区（或 cwd 变了）仍会被内置 ask 拦，届时二选一：
  1. 把同一条规则复制到新工作区的 `.dsh\rules.yaml`；
  2. 走 `E:\自动关机工具\自动关机工具.exe X /t=N`（不命中规则，免审批）。
- `ask` 之所以变成"拒绝"，是因为本 profile 预设 `danger-full-access` 的 `approval: never`；若哪天改回可审批的预设，这条 allow 依然成立，不影响。
- 关机前仍要先把结果写进回复：会话会随关机终止，来不及补。
