# 2026-11-21 自动关机工具 MCP 服务（stdio）

## 目标

把「自动关机工具 / 定时关机」本体的能力包装成 MCP 服务，让 DSH（以及任何 MCP 客户端）能直接
调用关机 / 重启 / 注销 / 睡眠 / 关屏 / 定时任务，而不是每次都去 shell 里敲 exe。

用户原话（2026-11-21）：

> 可以把咱们这个自动关机工具写一个 MCP，毕竟就是咱们自己写的软件嘛，可以供咱们调用。
> 写成插件以后，像定时关机定时重启什么的都可以直接调用这个软件来做

## 方案取舍

| 方案 | 结论 |
|---|---|
| MCP 服务里 spawn `自动关机工具.exe X /t=N`（包装 CLI） | **放弃**。CLI 的 `/t` 是阻塞打印剩余秒数的，一个 10 分钟的定时会占住 RPC 十几分钟；而且每次调用都要重新起一个 12MB 的 onefile 进程（解压 3–6 秒） |
| MCP 服务 `import core.actions` 进程内直调 | **采用**。与 GUI 同一份代码、同一个 `logs/app.log`、同一套 `safe_close_windows`；毫秒级，不阻塞 RPC |
| 定时交给 GUI 的 `timer_engine` | **放弃**。那是 Tk 线程 + 窗口生命周期绑定的，MCP 进程里没有 Tk |
| MCP 自带调度线程 + `tasks.json` 落盘 | **采用**。宿主拉起即可独立守时，宿主重启自动恢复 |

## 实现

新增 `E:\自动关机工具\mcp\server.py`（约 750 行，纯标准库，零第三方依赖）。

- **传输**：stdio + 按行分隔的 JSON-RPC 2.0，兼容 `server/discover`（回空 result 让客户端走 legacy `initialize`）、`initialize`、`ping`、`tools/list`、`tools/call`。
- **10 个工具**：`power` / `schedule` / `list_tasks` / `cancel_task` / `cancel_shutdown` / `notify` / `run_program` / `play_sound` / `status` / `open_gui`。
- **执行层**：直接 `from core import actions`，复用 `shutdown / restart / logoff / sleep / monitor_off / run_program / play_sound / show_message`；审计写 `audit()`，与 GUI 同格式。
- **调度**：`Scheduler` 线程 0.5 秒轮询；支持 once / daily / weekly(weekdays)；触发后写 `last_run` / `last_result` / `runs`，循环任务顺延下一次。
- **持久化**：`mcp/tasks.json`，写临时文件再 `os.replace` 原子替换。
- **零阻塞**：所有带 `delay_seconds` / `at` 的调用只落任务立即返回，不 sleep。
- **自检**：`python mcp/server.py --selftest` 不需要宿主即可跑一遍（列工具 + status + 建任务 + 撤销 + 弹气泡）。

### 坑 1：Windows 管道默认 GBK，中文 JSON 变非法字节

第一版用 `sys.stdout.write(json.dumps(..., ensure_ascii=False))`，DSH 侧 `tools/list` 整批读取失败、
连接显示"目标服务拒绝连接"。原因是 `sys.stdout` 在管道里默认走 ANSI 代码页（cp936），
中文被编成 GBK 字节，宿主按 UTF-8 解码炸掉。

**修法**：`_write()` 改成 `sys.stdout.buffer.write(json.dumps(...).encode("utf-8") + b"\n")`；
读入也改成 `sys.stdin.buffer.readline()` + UTF-8 解码 + GBK 兜底。

### 坑 2：`status` 里的 `shutdown /a` 是有副作用的

第一版为了判断"有没有系统关机排队"，在 `status` 里直接跑 `shutdown.exe /a` —— 那条命令本身
就会撤销用户已排队的关机。虽然当时就 `log.warning` 记了一笔，但只读接口不该改状态。

**修法**：`status` 不再探测，直接返回"未探测（请用 cancel_shutdown）"；撤销统一由 `cancel_shutdown` 负责。

### 坑 3：`cancel_shutdown` 把 1116 当失败

`shutdown /a` 在"本来就没有进行中的关机"时返回 1116，这是正常态而不是错误。

**修法**：`ok = code in (0, 1116)`，并在 `detail` 里带上系统原文。

## 接入 DSH

用 `dsh-mcp-connector` 插件（不是手改 `cordis.patch.yml`）：

```
mcp_connector_configure {
  name: "自动关机工具", serverName: "auto-power", transport: "stdio",
  command: "E:\\自动关机工具\\.venv\\Scripts\\python.exe",
  args: ["E:\\自动关机工具\\mcp\\server.py"],
  cwd: "E:\\自动关机工具", scope: "global"
}
```

落库位置：`<DSH_HOME>\storages\mcp_connector.json` → `tables.connections["custom-auto-power"]`
（`injectionMode: always`，所以新会话自动带上，不用手动激活）。

工具名：`mcp__auto-power__<tool>`。

`mcp_connector_reconnect` 对这条 stdio 连接一直报

## 已知限制

1. **MCP 服务是被宿主拉起的**：DSH 退出 → MCP 进程跟着退出 → `tasks.json` 里的定时在宿主再次启动前不会触发
   （启动后会立刻补跑已经过期的任务，不会丢）。要"关掉 DSH 也照样准时关机"，还是得用 GUI 的定时或 Windows 任务计划。
2. **MCP 进程与 GUI 可同时运行**，两者都能执行操作（MCP 进程内直调不受单实例互斥影响）。
   同一时刻别让两边下同一条关机指令，会各执行一次（第二次通常是 `shutdown 1190 已有关机在进行`，无害）。
3. `cancel_task` 只能取消**本 MCP 服务**的任务，GUI 里建的定时不在此列；要撤销系统层面的排队关机用 `cancel_shutdown`。
